# Changelog 0.50 to 0.55

Archived entries of mkvgo 0.50.x to 0.55.x, as they were published. The current versions are in [CHANGELOG.md](../CHANGELOG.md).

Versions 0.12.1 to 0.55.1 are retracted in go.mod.

## [0.55.1] - 2026-10-17

### Fixed

- **A subtitle read passes over a short damaged region instead of losing the
  whole track.** A Matroska file zeroed over a stretch (the pieces a download
  never received) failed every subtitle extraction with "damaged region at
  offset ...", so a player got no subtitle at all for the track. Every
  subtitle read (`ExtractSubtitle`, `ExtractASS`, `ExtractSubtitleWebVTT`,
  `ForEachSubtitlePGS` and their `From` forms, `BuildSubtitleIndex`,
  `SubtitleIndex.Resolve`) now resumes on the next Cluster when it lies within
  the new `Options.DamageBytes`, 64 MiB by default as for the on-demand HLS
  windows: the cues inside the region are lost, a PGS cue it left on screen
  is not stretched over it, and the rest of the track is delivered. Each
  region is reported once through `Options.OnSkip`. A longer region still
  fails with `reader.ErrDamagedRegion`; a negative `DamageBytes` refuses any
  damage. `reader.DamageRange` gains `FromMs` and `ToMs`, the timestamps of
  the clusters around the region. CLI: `extract-subtitle` and
  `subtitle-index` take `--damage-bytes` and name each region on stderr.

## [0.55.0] - 2026-10-17

### Security

- **SEC-01: an MP4's moov is capped at 256 MiB before it is read.** The
  metadata path allocated the moov's declared size in one piece, bounded only
  by the source's size: over `httpfs` that size is the server's Content-Range
  total, so 16 bytes of header claiming a terabyte asked for a terabyte, and a
  server streaming zeros under a 300 MiB moov made the probe allocate 1.3 GiB.
  A moov declared past `Options.MaxMoovBytes` (new, 0 = `DefaultMaxMoovBytes`,
  256 MiB) is now refused before any of it is read, on every MP4 path, with an
  error naming the option; under the cap the lazy read is used as before.
- **SEC-02: `httpfs` keeps only the range it asked for.** Under a
  `mkv.ShareReads` scope, `Stat` fetches the first and last window and sized
  each buffer from the Content-Range the server sent. A response is now taken
  only when it answers the request (the head starts at 0 and ends within the
  window, the suffix ends at the object's last byte and spans at most a
  window) and its Content-Length matches, so nothing past a window is
  allocated.
- **SEC-03: an `s3://` bucket can no longer move the signed request to
  another host.** In the default virtual-hosted style the bucket was written
  raw in front of the endpoint: `s3://evil.example?/k` sent the signed
  request, access key id and session token included, to `evil.example`. A
  bucket must now follow the S3 naming rules (3 to 63 characters of
  `[a-z0-9.-]`, a letter or digit at each end, no `..`, not an IPv4 address),
  and the URL built must name the endpoint's host.
- **SEC-04: credentials do not follow a redirect.** `s3fs` followed a
  redirect to any host and signed every hop; it now returns a 3xx as an error.
  `httpfs`'s default client (it used `http.DefaultClient`) refuses a redirect
  to another host while `Options.Header` is set. New `httpfs.Options.AllowHost`
  vets the host of every request and redirect, for a service that opens URLs
  its users supply (server-side request forgery, see the package doc).
- **SEC-06: encryption keys no longer have to go through argv.** `to-hls`,
  `hls-segment` and the other commands taking the HLS security flags accept
  `--aes-key-file` and `--cenc-key-file` (hex, whitespace ignored), and fall
  back to `MKVGO_AES_KEY` / `MKVGO_CENC_KEY` when the encryption is asked for
  without a key flag. A key on the command line is readable through `ps` and
  `/proc` and kept in the shell history; `--aes-key` and `--cenc-key` remain,
  documented with that risk.
- **SEC-07 (CLI): CENC packaging refuses to put the key in the playlist by
  default.** Without `--cenc-key-uri`, the `EXT-X-KEY` line carried the content
  key in clear as a `data:` URI. The CLI now exits with an error naming
  `--cenc-key-uri`, and `--cenc-inline-key` keeps the inline key for local
  testing. The library default is unchanged.
- **SEC-08: `mkvgo serve` caps its concurrent walks and turns CORS on only
  when asked.** The command ran with no cap on the windows built at once, so
  a burst of requests held as many windows in memory, and it sent
  `Access-Control-Allow-Origin: *` on every response, letting any web page
  read what a local server serves. `--max-walks` now defaults to the number
  of CPUs (`--max-walks 0` removes the cap), and `--cors` (on `serve` and
  `serve-growing`) adds the CORS headers. The library defaults are unchanged.
- **NEW-05, NEW-06: 'cenc' packaging reused the AES-CTR keystream across
  tracks and ABR variants; content packaged this way must be re-packaged
  under new keys.** The per-sample IV was the base IV plus the sample's decode
  timestamp in its own track, and every track and ABR variant shares the key:
  the first video sample and the first audio sample both took the base IV, as
  did every pair of samples at equal timestamps, and every ABR variant
  repeated the first one's IVs. The same key and IV under AES-CTR is a
  two-time pad: XORing the two ciphertexts gives the XOR of the two plaintexts,
  and a predictable one (silent audio, a known header) reveals the other.
  Affected: everything mkvgo 0.54.0 or earlier packaged with
  `CENCOptions{Scheme: "cenc"}` (CLI `--cenc-scheme cenc`) holding more than
  one track (video plus audio) or more than one ABR variant under one key.
  Re-package it with a new key, and rotate the old key out of the license or
  key server: re-packaging under the old key does not help, the ciphertexts
  already published stay exposed. `cbcs` is not affected (its constant IV is
  the scheme's design and its pattern encryption runs CBC, not CTR). Each
  track but the video now adds its own value in the IV's top byte, and each
  variant past the first its index times 2^48, so no IV serves two samples
  under one key.
- **NEW-07: VP9 CENC protects whole AES blocks per frame.** The VP codec
  ISO media binding requires each frame's encrypted bytes to be block-aligned,
  the clear bytes before them taking the remainder; the splitter protected
  everything after the uncompressed header, so a frame's protected run (and,
  in a superframe, the counter state of the next frame) was off by up to 15
  bytes. The clear prefix now takes the remainder.
- **SEC-05: single-source forensic marking is requalified as experimental.**
  `ForensicPlan` (CLI `forensic-segment`, WASM `openForensic`) picks the frame
  variant B drops without a key, and `DropNonRefSample` is exported: a lone
  viewer can turn every A segment into its B and erase the session pattern,
  and viewers comparing segments see which carry a bit. The Go doc, the CLI
  help, the docs and the README now call it experimental session marking,
  robust neither to collusion nor to re-encoding. `DropNonRefSample` is
  deprecated. The algorithm and its output are unchanged.
- **SEC-09: the explicit AES-128 IV is documented as reused.** `HLSKey.IV`
  and `HLSEncryption.IV` apply one IV to every segment of a key's period,
  which under CBC shows where two segments' plaintexts start alike. The doc
  now says so and recommends the default per-sequence-number IV. No output
  changes.

### Fixed

- **NEW-04: an in-place repair that dies while landing its journal is
  recoverable.** `ReindexInPlace` appended the new Cues, the journal and its
  trailer in three write calls, `RetimeTracksInPlace` the journal in two: a
  process dying between them left bytes past the original end with no trailer,
  so `RecoverInPlace` found nothing to undo while the next `ReindexInPlace`
  refused the file over that tail, and the error said to run `RecoverInPlace`.
  The tail now goes out in one write call: a death before or after any write,
  of the repair or of a recovery, comes back to the original file or the
  finished one, which a test checks at every write. A write torn partway (a
  power loss) is covered too for `ReindexInPlace`: before appending, it writes
  and syncs a 64-byte intent record (the original size, CRC32C) in the free
  tail of the head Void it already needs, and clears it before dropping the
  journal; recovery cuts the file back to that size, or clears a record the
  crash cut short. A test tears the writes at every byte (451 cuts) and gets
  the original or the finished file each time. `RetimeTracksInPlace` needs no
  head Void and keeps the one-write rule only.
- **NEW-03: a box named `sidx` is read only if a sidx can be that large.**
  The fragmented-MP4 keyframe scan read every `sidx` before the first
  fragment whole, whatever its declared size: a source delivering a 64 MiB box
  of that name cost 248 MiB of allocations (a remote server can stream it at no
  cost to itself). A sidx holds at most 65535 references (786,452 bytes); a
  larger one is skipped.
- **NEW-02: `mux` and `join` name the right flag when `-o` lacks its value.**
  They exited with `-t needs a value` and `-pattern needs a value`; both now
  say `-o needs a value`.
- **CLI-02: a value flag given last is an error, not ignored.** In most
  commands a flag taking a value (`-segment`, `-o`, `--aes-key`, ...) placed
  as the last argument was dropped in silence: `to-hls in.mkv -o out -segment`
  ran with the default segment length and exited 0. Every such flag now exits
  1 with `<flag> needs a value`.
- **ROB-05: the block reader refuses an EBML header of absurd size up
  front.** `NewBlockReader` skipped the header body by its declared size: an
  unknown size (-1) was skipped as nothing, misplacing every offset after it,
  and a size of 2^40 read the whole source before failing. A size outside 0 to
  1 MiB is now an immediate error.
- **ROB-04: an MP4 header duration no longer overflows into a negative one.**
  The mvhd, mehd and mdhd durations were converted as `ticks*1000/timescale`
  in int64, which wrapped for any duration past about 9.2e15 ticks although
  the guard let through up to 2^62: a version-1 header could report a
  negative movie or track duration. The conversion now runs in 128 bits, and
  a result past int64 is taken as unset.
- **ROB-03: a zero-length float reads as 0.** RFC 8794 lets a float element
  hold no bytes, meaning 0; `ebml.ReadFloat` refused it, so a file whose
  Duration (or any float) was written empty failed to open. It now returns 0.
- **ROB-02, NEW-01: a resync reads its region once.** `ResyncToCluster`, and
  the segment-level resync that recovers Info and Tracks behind junk, sought
  back and read a 64 KiB window again past every false candidate: a region of
  Cluster IDs that do not open a cluster cost a window per five bytes (8 MiB
  of them read some 100 GiB, one HTTP request each over `httpfs`). Candidates
  are now judged in the window already read, the few bytes one near its end
  needs carried into the next, so the region is read once. The offsets found
  are the same as before on generated data.
- **ROB-01: the trailing-Cues scan is linear.** On a Matroska file without a
  SeekHead, the reader looks for the index in the last 64 to 512 KiB by
  parsing forward from every candidate byte. A tail of empty Voids that does
  not reach the end made that quadratic: 12 s of CPU for 64 KiB, minutes for
  512 KiB, on every open of such a file. One backward pass now decides every
  start (0.6 ms for 64 KiB, 5 ms for 512 KiB), headers are decoded straight
  from the buffer, and the child checks inside CuePoints and ChapterAtoms draw
  on a budget in proportion to the window. The scan decides as before on every
  fixture and on generated tails.
- **A window is served past a short damaged region instead of refused.** A
  file holding a zeroed stretch (the pieces a download never received: 11 MB
  of zeros then debris, seen in the middle of a 3 GB film) failed every window
  touching it with `invalid VINT: leading zero byte`, and a server marked
  itself failing on three such refusals in a row. The block reader now
  classifies a header that does not decode in the middle of the file as the
  damage it is (`reader.DamageError`, `Offset` and `Resume`), the same as an
  element overrunning the file, and never the source's own failure (I/O, a
  cancelled context, a replaced file). The on-demand window walks pass over a
  damaged region shorter than `Options.DamageBytes` (64 MiB by default; CLI
  `--damage-bytes` on `hls-segment` and `abr-segment`): the window holding
  its start serves what it read before it, less the block the region cuts
  (its payload runs into the zeros), and closes on that track's frame
  duration rather than on a frame stretched to the far side of the region; a
  window whose cue points into the zeros is timed where it starts (an empty
  window was timed at the track's end, 6717 s for a frame at 2834 s); the
  video resumes on the first keyframe past the region, never on frames whose
  references it lost, and keeps a timeline without holes: a window the
  region emptied serves a copy of that keyframe every second, a window it cut
  short a copy of its own opening keyframe from where its frames stop, a
  still image where the video was lost (hls.js seeking back over empty
  fragments looped on them and never loaded the next one); known limits:
  the copies are the keyframe byte for byte, so an H.264 IDR repeats its
  idr_pic_id in consecutive IDR access units and an HEVC CRA repeats its
  picture order count, which the standards forbid; Chromium (hls.js, MSE)
  and FFmpeg decode them, hardware decoders (VideoToolbox in Safari,
  MediaCodec under ExoPlayer) are untested and need a run on a damaged file
  before relying on it; the audio is not filled: with hls.js handling the
  audio, playback stalls at the audio hole and seeks over it, skipping the
  frozen stretch; the windows behind it are whole, and the plan remembers the region so
  no later window scans it again. A served real file (a 1080p film zeroed
  over 11 MB) now decodes without error and plays through the hole in
  hls.js, where it stalled on the stretched frame. A longer region is
  refused as before, the error matching `reader.ErrDamagedRegion` with
  `Resume` -1 so a server can tell a damaged file from a failing server.
  `HLSPlanStats.DamageSkips` and `DamageRefusals` count both. The full
  passes (`RemuxToMP4`, `RemuxToHLS`) keep refusing a file damaged in its
  middle, now with the repair named. `BlockReader.SetDamageScan` bounds how
  far a walk looks past an unreadable element; `SkippedRanges` names the
  regions a `SetSkipDamage` walk passed over.
- **What a plan served is counted on the streaming path too.** `ServedBytes`
  only counted the segments `Resource` built whole: a server streaming every
  segment through `HLSPlan.Open` read it at 0 while it served megabytes, with
  no figure to set against `SourceReadBytes`. What `Open` hands out beside
  `Resource`'s is now `HLSPlanStats.StreamedBytes`: a segment streamed from
  the source counted as it is written, a kept segment, a playlist, an init or
  a subtitle counted whole when opened. `ServedSegments` counts the media
  segments handed out, whole by `Resource` or opened by `Open`. `ServedBytes`
  keeps its meaning (what `Resource` handed out), so the window accounting it
  belongs to is unchanged.

### Documentation

- **DOC-01: key rotation is called compartmentalization, not forward
  secrecy.** A rotated AES-128 key is one of a fixed list, cycled: a leaked
  key decrypts every period it serves and nothing protects past periods once
  the list is known. `HLSEncryption`, `--aes-rotate-segments` and the
  library, WASM, recipe and TypeScript docs now say a leaked key decrypts
  only the periods it serves.
- **DOC-05: the Go Report Card badge is gone from the README.** The service
  has been sunset.
- **DOC-02: the README command table lists every command.** Thirteen were
  missing (`analyze`, `fingerprint`, `track-ends`, `playability`, `ladder`,
  `ingest`, `extract-frames`, `subtitle-index`, `abr-segment`, `concat-hls`,
  `concat-segment`, `serve`, `serve-growing`); a test now fails when the table
  and the CLI's command list differ.
- **DOC-03: the `v{k}/<name>` and `mp4.PlanABR` paragraph sits under
  `abr-segment`** in docs/cli.md, where it belongs, instead of closing the
  `forensic-segment` section.
- **DOC-04: the `mkvhttp` package doc says what it caches.** It promised
  "long-lived caching for the deterministic outputs" and a strong ETag; the
  handler serves everything `no-cache` by default (immutable segments only
  with `Options.Immutable`) and streams media segments under a weak ETag. The
  package doc and streaming.md now say so.

### Changed

- **NEW-05, NEW-06: 'cenc' output bytes change for every track but the
  video and every ABR variant but the first.** Their IVs move to their own
  domain (see Security); a cache or CDN holding segments packaged before this
  release must drop them together with the init and playlists of the same
  presentation, as the re-packaging under a new key requires anyway. The video
  of a single presentation and of an ABR one's first variant keeps its bytes.
- **CLI-03: every command reads its flags through a `flag.FlagSet`.** The
  33 hand-written argument loops are replaced by one `FlagSet` per command,
  read with mkvgo's syntax (a value as the next argument, flags and operands
  in any order, each flag under its registered spellings only): the accepted
  arguments, results and messages are unchanged, checked against the previous
  parser on 20,000 generated argument lists and on the CLI suite.

- **Recycled buffers are poisoned under test.** Built with the `mkvgo_poison`
  tag, every buffer handed back for reuse (a block's payload buffer, a
  window's in-place arena, the serving pools, a cluster body) is filled with
  0xDB and replaced by a fresh one, so code holding a block's bytes past the
  reader's next block reads garbage and fails instead of passing on a lucky
  memory layout. CI and `make preflight` run the whole suite in this mode;
  the default build is unchanged.

## [0.54.0] - 2026-10-16

### Changed

- **A streamed window is read once.** The walk that builds a window's table
  for `HLSPlan.Open` reads the whole window (every payload of a 1080p film
  sits under the reader's seek threshold), yet its segments were then copied
  from the source again: a viewer taking video and one audio track read 2.56x
  the bytes served, measured per range on a 1080p film, and under a saturated
  disk the second read no longer came from the page cache. The walk now keeps
  what it read - the video segment and each audio segment of 2 MiB or less,
  each for the first `Open` that asks for it; the other languages go once a
  viewer took the video and one audio - and serving the window reads the
  source once: 1.21x the bytes served on that film (the window once, the
  other language and the subtitles with it), 3.17x down to 1.70x on a 2160p
  remux. The kept segments are budgeted process-wide, apart from the table
  cache (`mp4.SetWindowBytes`, `serve --window-bytes <MiB>|off`, default 256
  MiB, held by tables and by handles until written whole or closed): a window
  built while the budget is full is kept headers only and copied from the
  source as before. `HLSPlanStats.KeptSegments` and `KeptFallbacks` count
  both; a kept handle's `Bytes()` is nil (write and close it) and its ETag is
  the weak one of a streamed segment.

### Fixed

- **A window no longer walks the rest of the file for a track that is not
  there.** The walk that builds a window stopped only once every track of the
  plan had a block past the window's end. A track that ends before the video
  never has one, so every window after its end read the source to its last
  byte (22.7 MiB for a 2.8 MiB window on a 60 s source). A file written track
  by track from some point on - interleaved for its first minutes, then every
  video cluster, then every audio cluster, the audio uncued - made the window
  crossing that point walk the whole video tail to reach its audio, once per
  audio track: 4.1 GB read to serve 6.6 MB of a 2.9 GB UHD episode, measured
  on a real file, and under load the segment timed out. Now a track whose
  Cues stop two cue gaps before a window is not waited for; the one walk that
  meets the end of the source teaches the plan where each track ended; and a
  track still missing two windows past the window's bytes is looked for in
  the uncued regions of the source (the clusters the Cues never name, between
  or after the cued ones), where a track stored apart from the video lives:
  the window straddling the change reads about three windows' worth, the
  windows after it one, as on an interleaved file. `HLSPlanStats.FarLookups`
  and `FarHits` count those searches. The segments are the same bytes.

## [0.53.0] - 2026-10-16

### Added

- **The MP4 probe describes every track**, whatever a remux can do with it.
  A file whose tracks were all protected or of a codec mkvgo cannot carry was
  refused ("no convertible tracks found in MP4": 146 of 900 files of the
  public test corpora - CENC/cbcs `encv`/`enca`, MPEG-H, AC-4, IAMF, AMR in
  3GP, TTML). Such a track is now listed with what its entry states - the
  codec or the raw fourcc, language, duration, channels and rate or picture
  size (an AMR entry is mono whatever its reserved channelcount says; an
  MPEG-H entry's channel count comes from its `mhaC` reference layout; a
  ProRes entry's bit depth is its fourcc's, 10 up to HQ and 12 for 4444,
  none for ProRes RAW) - and
  a protected entry is read through its original format (`sinf`/`frma`) with
  `Track.Encryption` naming the scheme (`cenc`, `cbcs`; JSON `encryption`). `RemuxFromMP4` refuses such a track by name (set
  `Options.SkipUnsupported`, the CLI's `from-mp4 --skip-unsupported`, to drop
  it with a reason); the on-demand plans and `to-hls` refuse it through the
  same track plan (`to-hls --skip-unsupported` drops it). A `subp` handler
  (VobSub in MP4) is a subtitle track, described and refused by name rather
  than dropped as a non-media handler. Only a still picture (cover art) and a
  non-media handler remain `DroppedTrack`s.
- **PCM in MP4/MOV is carried into Matroska**: `twos`, `sowt`, `raw `,
  `in24`/`in32`/`fl32`/`fl64` (with the `enda` byte order), `ipcm`/`fpcm`
  (ISO 23003-5, by their `pcmC`) and the QuickTime version 2 `lpcm` map to
  `A_PCM/INT/BIG`, `A_PCM/INT/LIT` and `A_PCM/FLOAT/IEEE` with the bit
  depth. The one-frame samples are gathered into blocks of at most 1024
  frames that never cross a chunk, the packets the mainstream demuxer reads
  such a track in, so the remux is packet-identical. A layout Matroska has no
  form for (a big-endian float, a signed 8-bit or unsigned 16-bit integer,
  non-interleaved channels) is described and refused by name - never dropped
  in silence, as it was.
- **A Matroska `ContentEncryption` is read**: `Track.Encryption` names it
  (`AES-CTR`, `AES-CBC`, `DES`, ...; `unspecified` for a ContentEncodingType
  of 1 alone). `to-mp4`, `to-hls` and the plans refuse the track by name
  (`Options.SkipUnsupported` drops it) before touching a frame - an encrypted
  VP9 track was refused as a "bad frame_marker", an encrypted Opus or AV1
  WebM was remuxed into an MP4 no player decodes. The Matroska writer
  refuses to write a track it cannot keep encrypted.

- **`HLSPlanStats.SourceReadBytes`**: what the plan's requests have read from
  the source since it was built - every window walk, table, streamed segment
  and subtitle scan, through whatever reader the plan opens - so a server
  can sum what it reads over its plans where the process's I/O counters are
  out of reach.

### Changed

- **One rule for every remux, in both directions**: an audio or video track
  the output cannot carry fails the remux by name unless
  `Options.SkipUnsupported` drops it; a subtitle track it cannot carry never
  fails it and is dropped with its reason. `from-mp4` applied the first half
  to subtitles too and refused a file for its TTML (`stpp`) or VobSub track,
  where `to-mp4` and the HLS packaging drop an ASS or PGS track with a reason.
- **A fragmented MP4's duration is the fragments'.** The head-only probe read
  it from the mvhd, which a fragmented file leaves at 0 (67 files of the test
  corpora without a duration) or at its moov part alone (a partially
  fragmented file: 0.2 s for 1.16). It is now the `mehd`'s when the mvex
  states one, else the end of the fragments (last `tfdt` plus its trun's
  durations, per track), read from the moof headers alone; per-track
  durations follow.
- **A version 0 trun's composition offsets read signed**, as muxers write and
  demuxers read them: a negative offset read unsigned placed a frame 99 hours
  away and the remux failed ("outside SimpleBlock's int16 range").
- **`from-mp4` opens a new cluster when a decode window's presentation times
  spread wider than a SimpleBlock's offset can say**, instead of failing.
- **A fragment without `tfdt` continues where the track's previous fragment
  ended** (every such fragment restarted at 0, collapsing a 7.9 s file onto
  1.8 s), for the remux as for the probe's duration.
- **A track fragment that states no data anchor is read per ISO 14496-12**:
  a traf after the first, without `base_data_offset` and without
  `default-base-is-moof`, anchors on the previous traf's data end (every
  traf anchored on the moof before); when that places its samples past the
  fragment's data - files anchor such a traf on the moof anyway - the moof
  anchor is used, as the muxer meant.
- **`from-mp4` refuses a source without samples** (an initialisation
  segment) instead of writing a Matroska file without clusters.
- **Matroska audio defaults**: an audio track without `Channels` reads 1,
  without `SamplingFrequency` 8000 Hz (48000 for Opus) - the spec defaults
  every demuxer applies - once the codec's own header had its say: Vorbis,
  FLAC and Opus headers now fill the channels, rate and bit depth the
  container leaves out, like the AAC configuration did. A `SamplingFrequency`
  no file can mean (a corrupt float: 1.4e-37 Hz) is rejected, reported as
  unknown rather than as a value.
- **An unknown-size element that is no Cluster** (a live muxer's Cues, with
  its CuePoints of unknown size too) is walked to the element that ends it
  (RFC 8794: the first segment-level ID, the Segment's end or EOF) instead
  of refusing the file; its content is not read.
- **A video entry stating a 0x0 picture takes its size from the SPS** (H.264
  avcC, HEVC hvcC) and is refused by name when the codec configuration states
  none: Matroska PixelWidth/PixelHeight are mandatory and never 0 (a crashtest
  fixture went out as a 0x64530 track).
- **A display matrix with a column of no length is not a rotation**: a
  metadata track's `0 1e-5 0 0` matrix read as a 90° rotation; it is ignored,
  as ffmpeg ignores it.
- **A sample entry whose configuration is not what its codec needs** (an
  `mp4a` without decoder config, an `avc1` without `avcC`, a `stbl` without
  `stsd`) no longer fails the whole file: the track is described as it
  stands and the remux refuses it by name. The same for a track whose sample
  table the file cannot hold (a forged `stsz`, a moov cut from its media): a
  probe that used to pass because the track was ignored keeps passing now
  that its codec is carried.

- **`RemuxToHLS` reads the source once and writes the output once.** A full
  pass streamed every sample's bytes to one temp file per track, then copied
  them into the segments: the source was read once but the media written
  twice and read back once (a 4.4 GB source: 9.2 GB read, 9.2 GB written for
  a 4.6 GB presentation). A local source is now walked by its block headers
  alone, each sample's place recorded, and read once at those offsets as the
  segments are written, in 1 MiB writes - 4.7 GB read, 4.6 GB written,
  segments byte-identical, half the system time. A network source
  (`Options.SourceAccess`, else the file's mount), a compressed track or a
  converted one keeps the temp file.
- **`to-mp4 --faststart` reads the source once.** The sizing pass that
  places the moov first read the whole source before the write pass; it
  walks the block headers now, reading each track's first frame alone (a
  4.4 GB source: 9.2 to 4.7 GB read), a hashed track (`--hash`) still
  reading its bytes.
- **`RemuxFromMP4` reads a track's samples by runs.** An MP4 stores a
  track's samples in runs (its chunks); `from-mp4` read them one call each,
  two system calls a sample. The samples are now read through one 1 MiB
  window per track, a sample served by whichever window holds it, so an
  interleaved file is read once, in order: 5,346 to 46 read calls on a
  30 MB file, the bytes read unchanged, the output byte-identical.
- **`demux` writes in 1 MiB calls** (64 KiB before, which a video frame
  alone overflowed): 63,900 to 4,400 write calls on a 4.4 GB file.
- **`mp4.OpenMeta` parses a QuickTime chapter track only when the file has
  no `chpl`**, instead of reading its sample table on every open.

## [0.52.0] - 2026-10-15

### Added

- **`Options.SourceAccess`: how the source is reached.** `SourceAuto` (the
  default) decides from the source whether a streamed segment is read as
  from a local disk or across a network (see the network entry below);
  `SourceLocal` and `SourceNetwork` impose it, for a caller that knows its
  library. CLI: `serve --source-access auto|local|network`.

### Changed

- **`HLSPlan.Open` streams AES-128 segments.** A plan with `Options.Encrypt`
  built every segment in memory to encrypt it (the plaintext, then a padded
  copy). Its segments are now written from the source and encrypted with CBC
  as they go: the size is known before the first byte (PKCS#7 pads to the next
  16-byte block), keys, IVs and rotation are unchanged, and a range is
  encrypted from the segment's start, what precedes it thrown away. A failing
  source ends the write with an error after ciphertext only, and the pooled
  buffers that held plaintext go back zeroed. Measured on a 2 GB 1080p H.264
  source, 16 segments built at once for 15 s: MP4 peak memory 791 to 31 MB,
  16.9 to 12.9 ms a segment; Matroska 1,549 to 105 MB, 53 to 13 ms. The bytes
  are `Resource`'s; ffmpeg decrypts them to the source's packets.

- **`HLSPlan.Open` streams CENC segments, cenc and cbcs.** `Open` reads a
  segment's video samples once to find their subsamples and frame the `moof`
  with its `senc`, `saiz` and `saio`; each write then reads the samples again
  and encrypts them one at a time, so memory is bounded by the largest sample,
  and a range skips the samples before it. IVs, counters and subsamples are
  `Resource`'s, ranges included, and ffmpeg's `-decryption_key` decrypts them
  to the source's packets (four-slice H.264 included). Measured as above: cenc
  MP4 1,162 to 129 MB, 16.6 to 5.6 ms a segment; Matroska 2,054 to 250 MB,
  64.6 to 7.2 ms; cbcs MP4 1,081 to 170 MB, Matroska 1,775 to 261 MB and 118
  to 43 ms, but MP4 37.7 to 42.7 ms (see below). On a NAS over SMB, a video
  segment pays the second read: p50 95 to 106 ms and 75 to 79 ms on two
  files, p95 unchanged or lower; its audio, read through the gaps, 213 to 72
  ms and 44 to 20 ms.

### Performance

- **cbcs encryption no longer allocates per block.** The 1:9 pattern
  encrypted each one-block crypt run through a new CBC encrypter, one
  allocation per protected block: thousands a segment, and the collector
  behind them. The chain now runs block by block in place, the bytes
  unchanged. Measured as above, cbcs through `Open`: MP4 37.7 to 5.6-6.1 ms a
  segment, 170 to 78-86 MB; Matroska 43 to 8.8-8.9 ms, 261 to 181-238 MB.
  `Resource` and the full pass gain the same way.

- **A streamed CENC segment reuses its sample and write buffers.** Each
  request allocated a 64 KiB write buffer and grew a sample buffer of its own;
  both now come from pools, the sample buffer zeroed on its way back (it held
  plaintext). Measured as above, 16 segments built at once: cenc Matroska 98
  to 81-84 MB, MP4 120 to 66 MB; cbcs Matroska 59 MB. What a CENC segment
  still allocates per request is its moof (the senc and subsample tables are
  the segment's own) and a CTR state per sample.

- **A network source keeps its round trips down.** On a network mount (NFS,
  SMB, 9p, Ceph, AFS, or a FUSE mount of a network kind - rclone, sshfs, s3fs,
  gcsfuse, davfs... - told by its subtype in mountinfo; a mergerfs pool is
  local) or a source that is no local file, read-ahead is not
  asked for (it would fetch whole ranges across the network ahead of need),
  an audio segment's reads go out together (8 at a time, into one buffer of
  at most 4 MiB), and a Matroska window's light audio is kept with the walk
  that reads it, as before, rather than read again from the file: there each
  read is a round trip, not a page-cache copy. Measured on a NAS over SMB,
  every segment of two Matroska files requested once, cold: audio p50/p95
  150/317 ms in 0.51.0, 175/314 ms with the audio copied from the file, and
  139/287 ms now.

- **A cached window table keeps its samples packed.** A Matroska window's
  table held, for every sample, a full fragment record and its offset - 86
  bytes a frame measured - and the plan's byte budget counted a third less
  than that. The samples now sit as varints, times and offsets as deltas,
  unpacked for the one rendition a request serves; the segment head stays as
  built, and the budget counts what is really kept. Measured on the 2 GB
  Matroska source, all 117 windows cached: 6.7 MiB to 0.9 MiB (12 bytes a
  frame); the `hls-server` example under 16 connections, peak memory 39-40 to
  29-31 MB at the same throughput (2,920-3,130 requests/s).

- **A Matroska source's audio is copied from the file too.** `Open` kept a
  window's audio, read with the structure walk, built whole in the window's
  table; the walk now reads every track's block headers only - a laced
  block's lace header, its frames skipped - and an audio segment is copied
  from each frame's place in the file, read through the small gaps as an MP4
  source's is. Measured on the 2 GB Matroska source: 16 segments built at
  once, peak memory 156-218 to 40 MB and 3.9 to 1.8 ms a segment (an MP4
  source: 41 MB, 2.0 ms), AES-128 105 to 39 MB, cenc 250 to 117 MB; the
  `hls-server` example under 16 connections, 76 to 40 MB at the same
  throughput (2,850 to 2,830-2,920 requests/s), every segment requested once
  in turn p95 4.7-5.0 to 3.9-4.0 ms. A track whose blocks are compressed
  (zlib) is served from memory, as its video always was.

- **A segment's bytes, and a Matroska window's, are asked for before they
  are read (Linux).** On a cold page cache each read waited for the disk in
  turn: the few hundred reads of an audio segment interleaved sample by
  sample, a video segment's frame-sized sendfile calls, and the header hops
  of a Matroska window's first walk. The ranges they will read are now asked
  for up front with posix_fadvise WILLNEED, in pieces of the device's
  read-ahead size (its read_ahead_kb, 128 KiB when it has none: the kernel
  reads at most that per call and drops the rest): a
  segment's requested range only, a Matroska window's span before its walk.
  Measured against 0.51.0 (the Matroska figures include the audio change
  above) with the server on 2 cores (GOMAXPROCS=2), page cache dropped, 60
  segments drawn at random over every rendition of the 2 GB sources, then the
  same 60 again: MP4 cold p50/p95 29.5/31.6 to 1.8/9.1 ms, warm 0.9/7.1 to
  0.9/6.6 ms; Matroska cold 43.1/80.4 to 4.9/12.0 ms, warm 1.2/7.9 to
  0.8/6.2 ms; a Matroska window's first walk, cold, 40-50 to 4-7 ms. Under
  16 connections, on 2 cores: MP4 2,934 to 2,937 requests/s; Matroska 2,390
  to 2,945 requests/s, p99 28.4 to 20.8 ms, peak memory 61 to 34 MB.

### Fixed

- **`WithInBandChannels` counts an E-AC-3 7.1 as 8 channels.** It read the
  first frame of the track's first block only: the access unit's independent
  substream - an E-AC-3 one, or an AC-3 core - carrying the 5.1, and not the

- **`Track.HandlerName`** (JSON `handler_name`): an MP4 track's `hdlr` name,
  as probers report it, apart from the title.

- **`Container.TrackLanguage(t)`**: the track's language with the Matroska
  default applied, the probe JSON's `resolved_language` (see Changed).

- **`Container.TrackCodecName(t)`**: the track's prober `codec_name` with
  what only the container knows (`mov_text` for an MP4 timed-text track).
  `Track.FFprobeCodecName()` is unchanged.

- **The TypeScript `Track` type** (`web/mkvgo.ts`) has `frame_rate_estimated`,
  `handler_name` and `language_present`.

### Changed

- **`resolved_language` is "eng" for a Matroska track that stores no
  language.** RFC 9559 makes "eng" the default of the Language element
  (LanguageBCP47, when present, wins over it). The probe and `tracks` JSON,
  CLI and WebAssembly, returned no `resolved_language` for such a track; it
  now resolves to "eng" on a Matroska or WebM file, with `language_present`
  still false. An MP4 track without language is unchanged.
  `Track.ResolvedLanguage()` and the HLS and DASH manifests are unchanged:
  a track that states no language gets no `LANGUAGE`, since it is often
  not English.

- **A SeekHead at the end of the file is followed, and a file it indexes is
  not read back from its end.** When the head SeekHead points only at a
  second SeekHead written after the Cues and Tags, `ReadMeta`/`OpenMeta`
  read that one, then the elements it indexes at their offsets, in file
  order, so elements stored together come in one read. A file whose
  SeekHead indexes the Cues, with no stale entry, no longer gets the read
  back from EOF; the read back is kept for files without SeekHead. A remote
  probe of a 4 MiB test file with 150 KB of Cues and a tag indexed that
  way: 4 requests and 960 KiB, now 3 requests and 660 KiB. Over the 497
  files probed remotely: the one file in that layout goes from 704 KiB to
  580 KiB, one other from 3 requests to 2.

- **The read back from the end of a file without SeekHead starts at
  64 KiB.** It read 512 KiB back from the end in one go, whatever the tail
  held. It now starts at 64 KiB and doubles, up to 512 KiB, only while the
  window ends inside metadata that starts before it; a file ending on a
  cluster stops at 64 KiB. A remote probe of a 4 MiB test file without Cues
  nor SeekHead: 2 requests and 1 MiB, now 2 requests and 576 KiB. Over the
  497 files probed remotely, bytes read go from 319.5 MiB to 302.5 MiB; 42
  files whose tail metadata exceeds 64 KiB make 1 or 2 more requests
  (1,022 requests in all, then 1,073).

- **A metadata read steps over a large attachment with exact reads.** Over
  HTTP the headers right after a skipped font opened a new 512 KiB window: a
  remote probe of a test file with a 760 KB font made 3 requests for
  1,025 KiB. Once the skipped payloads reach 256 KiB, `ReadMeta`/`OpenMeta`
  read through exact ranges (`io.ReaderAt`) of 4 KiB, doubled while the
  reads run on: 3 requests for 516 KiB. The WebAssembly `Blob` reader offers
  the same exact reads: 3 Blob reads of 128 KiB in all, now 3 of 68 KiB.
  Over the 497 files probed remotely the JSON and the requests are
  unchanged.
