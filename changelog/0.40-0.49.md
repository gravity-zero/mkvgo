# Changelog 0.40 to 0.49

Archived entries of mkvgo 0.40.x to 0.49.x, as they were published. The current versions are in [CHANGELOG.md](../CHANGELOG.md).

Versions 0.12.1 to 0.55.1 are retracted in go.mod.

## [0.49.0] - 2026-10-14

### Breaking

- **The WebAssembly results carry the 64-bit UIDs as strings.** `JSON.parse`
  turns an integer into a JavaScript number, which keeps 53 bits: a track
  UID, chapter UID, attachment UID or tag target of 7454167688999517126 read
  back as 7454167688999517000, and could not be matched or written back. The
  track `uid`, chapter `id`, attachment `id` and tag `target_id` are now
  decimal strings by field, whatever the value (a `uid` of 1 is `"1"`); any
  other integer beyond 2^53 - 1 in any result is a string too, and track
  numbers and the other fields stay numbers.
  The TypeScript types say so (`Track.uid`, `Chapter.id`, the attachment
  `id`, the new `Tag`). A caller that compared these fields with numbers
  compares strings now. The rewrite is one pass over the JSON bytes: a probe
  under Node 22 takes 1.19 ms on a 237 MB MKV and 1.86 ms on a 237 MB MP4
  with a 697 KB moov, against 1.15 and 1.80 ms without it.
  **Migration for JavaScript consumers:** with `web/mkvgo.ts`, `Track.uid`,
  `Chapter.id`, the attachment `id` and `Tag.target_id` are now typed
  `string`, so the compiler points at each use. Compare them with strings
  (`track.uid === '7454167688999517126'`, `chapter.id === '1'`), not with
  numbers; use `BigInt(track.uid)` where arithmetic is needed; pass them back
  as strings. A UID stored from an earlier release was already rounded and
  matches nothing: read it again from the file. Track numbers (`Track.id`,
  `track_id` options) stay numbers.
- **A remote `probe` of a Matroska file without Cues reads the head only.**
  `probe` asked for the complete keyframe index, which on a file without Cues
  is a walk of every Cluster: over HTTP or S3 that downloaded the whole file
  (measured on a 151.6 MB file: 15 requests, 152.1 MB transferred). A remote
  Matroska `probe` now takes its keyframes from the Cues alone and reports
  none without them: 1 request, 512 KiB. Its JSON therefore has no `keyframes`
  key on such a file, where it had one: the local `probe` never had it, and
  `keyframes` (on a local or remote file) still builds that index.

### Added

- **`HLSPlan.CueDensity()` says what a Matroska plan cut on.** A plan cuts
  only where a video cue points, so it matches the full pass only when the
  Cues index every keyframe. The new report gives the number of video cue
  points, the widest gap between two of them (and where it opens), the median
  gap, the last cue point, and whether `SynthesizeIndex` built them; an MP4
  plan reports `ok == false` (its sample table is exact). On a 13-minute file
  with a keyframe every 2 s whose Cues hold 312 of its 390 keyframes: 312 cue
  points, a 4000 ms widest gap against a 2000 ms median.

### Changed

- **An Opus track keeps its sync across MKV <-> MP4.** Opus-in-ISOBMFF makes
  the edit list (`media_time` = pre-skip) the trim of the priming samples, the
  `dOps` pre-skip being informative only, but `to-mp4` wrote no edit list for
  Opus and `from-mp4` dropped one it read. The pre-skip now travels as the
  edit list <-> Matroska `CodecDelay`, like AAC, in the progressive MP4, the
  HLS/DASH init and the MKV read back. Measured with a flash and a beep both
  at 2 s, decoded: `to-mp4` put the audio 6.5 ms late (now 0.02 ms, the
  source's), and `from-mp4` on an MP4 carrying the Opus edit list 7 ms late
  (now 0.02 ms). The fragmented init now carries the same edit list; the
  mainstream decoder used for the measurement ignores it on fragmented Opus,
  so its reading of the HLS output stays 6.5 ms late. `make e2e` checks the
  flash and the beep for AAC and Opus in both directions, within 1 ms.
- **A display rotation survives every remux.** Matroska carries it as
  `Video>Projection>ProjectionPoseRoll` (degrees counterclockwise), which was
  not read: `probe` of such an MKV showed no rotation. And no output carried
  one: `from-mp4` wrote no Projection, `to-mp4` and the HLS/DASH init segments
  an identity `tkhd` matrix, so a phone video played sideways after any of
  them. The roll of a flat video (rectangular projection, no yaw or pitch) is
  now read into `Track.Rotation` by both MKV parsers, the MKV writer writes it
  back (folded into (-180, 180]), and every `tkhd` the MP4 writer builds
  carries the matching display matrix. With display rotations of 90, 180 and
  270: `probe`, `from-mp4`, `to-mp4` (with and without `--faststart`) and
  `to-hls` (from MP4 and from MKV) report the source's angle on every output.
  `probe` prints the angle as "clockwise".
- **The WebAssembly remuxes take a `Blob`/`File`.** `remuxToMP4`,
  `remuxFromMP4`, `remuxToWebM` and `remuxToHLS` refused anything but a
  `Uint8Array`, so the whole input sat in memory twice (in JavaScript, then
  copied into the module) and was copied a third time into the in-memory
  filesystem. A `Blob`/`File` is now read through ranged slices, a
  `Uint8Array` is copied into the module once and read in place, and the
  output is reserved at about the input's size (`mkv.MemFS.Reserve`, below)
  so it is not grown by copies. `remuxToMP4` with `fastStart` on a 143 MB MKV
  under Node 22: the module's memory goes from 701 MB to 306 MB from a
  `Uint8Array`, and to 165 MB from a `File`; the peak RSS of the process from
  950 MB (1,798 MB before the in-memory output fix below) to 666 to 680 MB.
  The outputs are byte-identical.
- **`mkv.MemFS.Reserve` (new) sizes an in-memory output up front.** A writer
  that knows about how much it will write reserves it once, and the file is
  not grown by copies; the WebAssembly remuxes reserve their output at the
  input's size.
- **A WebAssembly remux from a `Blob` keeps a window on each region it reads.**
  The Blob reader cached one window, so an MP4 whose video and audio chunks
  sit in two regions of the file (not interleaved) dropped it on every jump
  between them and read it again: `remuxFromMP4` of a 143 MB `File` made
  4,499 Blob reads for 372 MiB. The reader now keeps four windows, the least
  recently used one replaced on a miss, each doubling while its region is
  read on: 294 reads for 143 MiB, 1.48 s down to 0.78 s and a peak RSS of
  878 MB down to 679 MB under Node 22. The outputs are byte-identical.
- **Writing an MKV allocates its cluster buffer once.** The MKV writer
  assembled every cluster in a fresh buffer grown by doubling, about twice the
  media it wrote in allocations, and the memory the runtime handed back to the
  system came back as page faults on the next clusters. It now keeps one
  buffer for the whole file. On a 1.8 GiB file (warm cache): `from-mp4` goes
  from 4.2 s (2.8 s system, 355,000 minor faults, 6.7 GB allocated) to 1.1 to
  1.7 s (0.8 s system, 15,000 faults, 2.0 GB), `merge-subtitle` from 3.8 s
  (2.5 s system, 291,000 faults, 7.1 GB) to 1.3 to 1.8 s (0.7 s system, 16,000
  to 26,000 faults, 2.0 GB). The other operations that write clusters
  block by block take the same path: `to-webm`, `split`, `join`, `mux`,
  `merge-ass` and the edits that rewrite the file (`RemoveTrack`, `AddTrack`,
  `EditMetadata`).
- **`MkvGo.probe` of a `Blob` starts with a 64 KiB read.** Every Blob read
  was a 512 KiB window, and on a file-backed Blob under Node 22 that read
  alone cost 0.74 ms where the whole probe of a small MP4 took 0.97 ms. The
  window now starts at 64 KiB, doubles while the reads run on, up to
  512 KiB, and starts small again after a jump; its buffer is reused. Probe
  per call: a 0.5 MB faststart MP4 1.14 ms down to 0.47 ms, the same file as
  MKV 1.06 ms down to 0.49 ms, a 6.9 MB MKV with 13 chapters and a font 1.99
  ms down to 0.68 ms.
- **`to-mp4` reads its samples into one buffer.** Each block was read into
  a buffer of its own, then copied into its track's chunk at once: the whole
  source allocated again on every pass (two for `--faststart`), and a chunk
  buffer that regrew from nothing on each pass. The walk now reuses one
  buffer for the blocks of a track whose sample entry is built, and the
  chunk buffer is allocated once at its flush size. On a 1.8 GiB file with
  `--faststart` (warm cache): 63,000 to 102,000 minor faults down to 5,000 to
  6,000, 0.4 s user down to 0.1 s, 1.1 to 1.3 s system down to 0.8 to 0.9 s;
  the output is byte-identical.
- **`split` reads its source once.** Every part opened the source again and
  read it from the top up to its own start, so the reads grew with the square
  of the part count: 13 parts of a 1.73 GiB file read 12.66 GiB. A part now
  continues the walk on the block the previous part stopped on, which is the
  keyframe a walk from the top would open on: the same split reads 1.79 GiB,
  and its 13 parts are byte-identical to before. Ranges that go back in time
  (an explicit `-range` list out of order) still read from the top.

### Fixed

- **The on-demand plan's byte-identity with the full pass is stated with its
  condition.** `docs/library.md` and `docs/cli.md` promised that every
  resource of a Matroska plan is byte-identical to `RemuxToHLS`/`to-hls`.
  That holds only when the Cues index every video keyframe: the plan cuts
  where a cue points, the full pass at every keyframe, so a boundary due on
  an uncued keyframe moves to the next cue (a file whose Cues hold 312 of its
  390 keyframes plans 8 s segments where the full pass cuts at 6 s: 117
  segments against 130). The docs now state the condition, the remedy
  (`reindex`) and that `SynthesizeIndex` does not replace sparse Cues.
- **`probe` of a Matroska file without Cues says it has no keyframe index.**
  The text output printed nothing at all, as if the line had been forgotten;
  it now prints `Keyframes: none (no Cues ...)`, with `mkvgo reindex` as the
  way to write one. Local and remote probes return the same index: none
  without Cues, in the JSON as in the text (before the remote-probe fix below, a
  remote probe of a 151.6 MB file without Cues returned 30 keyframes for 15
  requests and 152 MB read, where the local probe of the same file returned
  none).
- **`Track.Rotation` says which way it turns.** It counts degrees clockwise
  (a file made with a 90-degree counterclockwise display rotation reads
  270), where the Display Matrix side data it was documented against counts
  counterclockwise (90). The value is unchanged; the godoc, `docs/library.md`
  and `docs/cli.md` now state the clockwise convention and the conversion
  (`-Rotation` folded into [-180, 180)).
- **The documented artifact sizes are the real ones.** The README stated a
  binary of about 8 MB and release binaries of ~2.3 MB (the figure of the
  first commit), and the README and `docs/wasm.md` a WebAssembly module of
  ~6 MB, ~1.6 MB gzipped. Measured with the Makefile's flags: 10.6 MB for the
  linux/amd64 binary, 9.0 MB for the module, 2.4 MB gzipped. `make
  preflight` now runs `scripts/sizes.sh`, which builds both and fails when a
  stated size is more than 15% off.
- **An in-memory output grows like `append`.** A file written through
  `MemFS` (the WebAssembly build writes every output there) was reallocated
  and copied whole on each write that extended it, so writing an output cost
  time and memory in the square of its size. It now doubles its capacity, and
  a write past the end still reads back zeros between the old end and the
  write, even after a `Truncate`. `MkvGo.remuxToMP4` with `fastStart` on a
  143 MB MKV under Node 22: peak RSS 1,798 MB down to 950 MB, 1.5 s down to
  0.4 to 0.6 s, the output byte-identical.
- **A WebAssembly or remote probe reports chapters, tags and attachments.**
  `MkvGo.probe` promised the shape of the CLI `-json` output but read Info and
  Tracks only: a file with 13 chapters, 3 tags and a 760 KB font came back
  with none of them. The remote CLI (`probe`, `chapters`, `tags`, `attachments`
  on an `http(s)://` or `s3://` Matroska file) said they needed the local file.
  Both now read them head-only through the SeekHead or the bounded tail read,
  with the attachment list (name, MIME type, size) and not its payloads: the
  remote probe of that file reads 1 MiB in 3 requests, the font left on the
  server. `docs/library.md` gives the same read for a library scan: on that
  file it allocates 13 KB in 16 µs where `Open`, which reads every attachment
  payload, allocates 825 KB in 160 µs.
- **A cancelled Matroska plan stops reading.** The BANDWIDTH check, which
  reads the cluster headers of a segment whose span looks too large (up to 16
  headers for each of up to 32 spans), did not look at the context: a plan
  cancelled during it read every remaining header first. It now tests the
  context before each span and each header, and `PlanHLS` returns the
  context's error rather than a plan with spans left unchecked. On a 2160p
  film whose plan reads 262 cluster headers (cache warm): up to 261 reads
  after the cancel, returning after 18 ms median and 40 ms at most, down to
  none, returning after 0.22 ms median and 0.57 ms at most. `OpenMetaWithFS`
  now opens the file through `FS.OpenContext`: a plan cancelled before it
  no longer opens a remote source for its metadata. The cover-art attachment
  is read only while the context is live: a plan cancelled right before it read the
  picture (2 MiB on the test file) and returned a plan; it now returns the
  context's error. Without a cancel, the 7,066 resources of the plan
  (playlists, init, manifest and every segment) are byte-identical.

## [0.48.1] - 2026-10-13

### Fixed

- **`PlanHLS` on an MP4 source stops when its context is cancelled.** It
  never checked the context: a plan cancelled before the call, or while it
  walked the file's fragments, ran to the end and returned a plan. The context
  is now checked on entry (before the source is opened), before each read of
  the sample-table walk (a fragmented file reads each fragment, a large moov
  is read in pieces of 1 MiB), every 4,096 samples of the sample-table copy
  and once per track and per segment of the plan's later steps, and its error
  comes back as is (`context.Canceled`, not wrapped). Measured with a cancel
  at 20 points of a plan (warm cache): a 1,814-fragment file now returns
  within 3.4 ms of the cancel and a progressive 2160p file within 3.9 ms,
  where both ran to the end before; a cancel after the last check still
  returns the finished plan. Plan time is unchanged and every resource is
  byte-identical (2,219 and 3,892 resources). A Matroska plan whose context
  is already cancelled also returns the bare context error now.

## [0.48.0] - 2026-10-13

### Changed

- **An MP4 source's on-demand plan reads no subtitle text.** `PlanHLS` lists
  each text track's samples (mov_text/tx3g, wvtt) from the sample table alone
  and reads none of them; a WebVTT segment reads the cues of its own window
  the first time it is requested, then keeps them. A sample too short to hold
  text (tx3g of 2 bytes or less, wvtt of 16 or less) is skipped unread. On a
  2160p episode with two French tracks the plan went from 1,746 reads to 10;
  the playlists, the master, the DASH manifest and every WebVTT resource are
  byte-identical. **Behaviour change:** a subtitle sample that
  cannot be read no longer fails `PlanHLS`; the error comes back from the
  request for that subtitle resource (`Resource`, `Subtitle`, a windowed
  `subN_NNNNN.vtt`), and the video and audio keep serving.

### Fixed

- **A segment request whose context is already cancelled fails.** `Segment`
  and `Resource` on a plan returned the segment anyway, because the window
  build runs detached from the requester and noticed the cancellation too late;
  they now return the context's error first, built or cached. In WebAssembly a
  `segment()` given an aborted `AbortSignal` rejects again (broken since
  0.44.0).
- **`mkvgo serve` always shuts down cleanly on Ctrl-C.** It started listening
  before registering for the interrupt, so a Ctrl-C landing in between killed
  the process without the graceful shutdown; the interrupt is now registered
  first. Same for the growing-file server.

## [0.47.0] - 2026-10-12

### Added

- **`Options.NoIFrames`** (CLI `--no-iframes` on `to-hls`, `hls-segment`,
  `to-abr`, `abr-segment`): drops the trick-play I-frame stream from HLS
  packaging. No `EXT-X-I-FRAME-STREAM-INF` in the master (single and ABR), no
  `iframe.m3u8` written, listed or served (`Resource` refuses it), and no
  Matroska keyframe walk or I-frame collection behind it. Off by default; the
  segments and the other playlists are byte-identical either way. For servers
  whose players scrub with their own trickplay images, where a stray
  `iframe.m3u8` request would start a keyframe walk over the source.

### Fixed

- **A Matroska plan's master declared an I-frame `BANDWIDTH` below its own
  I-frames.** It was estimated from the first keyframe alone; a larger
  keyframe later in the film made the declared bit rate too low. It is now
  the plan's peak segment bit rate, which bounds every I-frame (each lies
  inside its segment, over the same duration).

## [0.46.0] - 2026-10-12

### Added

- **Batch keyframe extraction for trickplay strips**:
  `matroska.ExtractKeyframes` (a callback per sample) and
  `matroska.WriteKeyframeStream` (a keyframe-only Matroska stream for one
  decoder), CLI `mkvgo extract-frames`, for Matroska/WebM and MP4
  (progressive or fragmented: the sync samples stand for the cues, each read
  with one exact range; `mp4.VideoSyncSamples`). One metadata + Cues read and one
  source handle for the whole strip, keyframes read in ascending order, each
  payload once, buffers reused. Selection on the video cues: one keyframe every
  N ms (FFmpeg's `prev_selected_t` rule) or the keyframe at or before given
  times. Against a loop of `ExtractKeyframeSample` on 780-800 keyframes of a
  1080p and a 2160p film: bytes read 475/501 MB → 61/80 MB, 1562 opens → 2,
  CPU 1.3-1.4 s → 0.08-0.09 s, allocations 2 GB → 4-7 MB. Every sample is
  checked on its bitstream to be a picture a decoder can start on (a cue on
  anything else is counted as skipped, never emitted), and the samples decode
  back to back in order, one picture each: HEVC CRA and H.264 open-GOP
  keyframes get their picture-order fields renumbered in place (fed as is,
  FFmpeg output 740 pictures out of 795 CRA samples, out of order). Typed
  errors `ErrNoKeyframeIndex`, `ErrNoVideo`, `ErrUnsupportedCodec`.
  `scripts/keyframes_verify.sh` checks a source's stream against a full decode.

### Fixed

- **`ExtractKeyframeSample` could return a keyframe after the time asked**: it
  took the cue at or before the time among the cues of every track, and a
  subtitle cue between two video keyframes points at the next keyframe's
  cluster. It now looks at the video track's cues (a file that cues no video
  keeps the old lookup).
- **`ExtractKeyframeSample` on AV1** gives a temporal unit without its own
  sequence header OBU the `av1C` one: the IVF was undecodable alone.
## [0.45.0] - 2026-10-12

### Added

- **`mkv.RangeHinter`**: a reader told the byte range `[off, end)` its next
  reads cover. `httpfs` (and so `s3fs`) fetches it with one request instead
  of a window at a time; a hint is advice, reads outside it work as before.
  `mp4.PlanHLS` announces each window's range and the streamed copy its spans.
- **`mkv.ShareReads`** (`WithReadShare`, `ReadShareFrom`, `ReadShare`): a
  scope under which readers opened by an FS pass each other the bytes one of
  them already fetched. `PlanHLS` opens one while it builds a plan, never for
  segment reads, which must still notice a replaced source.

### Changed

- **Remote reads (`httpfs`, `s3fs`) stream the response body** instead of
  buffering a window, and a sequential read doubles its request (up to 32
  windows). A broken response resumes on the pinned version (`If-Match`, 4
  attempts at most, refused without a validator) and a short abandoned rest
  is drained so the connection is reused.
- **A remote `PlanHLS` makes no HEAD**: a reader's `Stat` under a read share
  fetches both ends of the file, its first responses give the size and the
  version, and two answers of different versions (ETag, `Last-Modified`
  without ETag, or total size) fail with `ErrSourceChanged` instead of
  mixing them. `ReadAt` reads one exact pinned range.
- **The bandwidth spans of a remote plan are checked with exact header
  reads, two at a time**, the head and the tail read in parallel. On a 50 ms
  link this step alone takes the master playlist of a film with Cues at the
  end from about 1.9 s to 0.9 s, and 9.9 to 1.0 MiB read; the playlist is
  byte-identical.
  A segment is one request per pass over its window (two when streamed).
- **`to-mp4 --faststart` writes a local source's output in one pass**: a
  sizing pass then a single `ftyp`+`moov`+`mdat` write, with no temporary
  `mdat` (half the bytes written, output byte-identical). A remote source
  keeps the temporary file, since it would be downloaded twice.

### Fixed

- **`subtitle-index -from-cues` no longer runs the full walk first**: the
  index came from the Cues but the CLI walked the file before using them.
- **The source stat interval of a plan runs on the monotonic clock**: a wall
  clock stepping back (seen every 30 s under WSL2) skipped the path stat,
  so a source replaced in that time was only caught by the read itself.
- `analyze`'s help and docs said it reads the head only; the walk reads
  about the whole file.

## [0.44.0] - 2026-10-11

### Changed

- **`mkvhttp` serves init and media segments `no-cache` by default**, and
  `FileHandler` its file, instead of `public, max-age=31536000, immutable`.
  A segment name is the same for a source replaced under the same path, so a
  year of immutable caching served the old file's segments against the new
  playlist; a client now revalidates on the ETag (a bare `304` when
  unchanged). `Options.Immutable` restores the old header for a handler
  mounted where the URL names the source's version, under the new
  `HLSPlan.SourceID()`; playlists and manifests stay `no-cache` either way.
  `examples/hls-server`, which announced `immutable` on its playlists too,
  now serves under `/hls/<SourceID>/` and redirects its entry points there.
- **`FileHandler`'s ETag adds the file's identity and it no longer sends
  `Last-Modified`.** The ETag stays strong, from the size and the mtime to the
  nanosecond as nginx, Apache and Caddy do, plus the device and inode: a file
  renamed over the served one with the same size and mtime answered `304`
  and a range of itself to a client holding the old one. A date validator
  cannot tell apart two versions within one second: `If-Modified-Since`
  answered `304`, and a dated `If-Range` a range, for a file replaced within
  that second; without `Last-Modified` both fall back to the whole file. A
  `Range` with `If-Range` on the current ETag still gets its `206`.

### Added

- `mkv.FS.OpenContext` and `DoOpenContext`: a reader whose requests end with
  a context. `httpfs` and `s3fs` set it, and the on-demand plans open their
  source through it with the walk's context, so a remote read in flight is
  abandoned once every client waiting on the walk has gone.
- `httpfs.Options.RequestTimeout` and `s3fs.Options.RequestTimeout`: each
  request is bounded, 60 s by default (`http.DefaultClient` has no timeout:
  a server that stopped answering held a walk and its slot for good).
- `mkv.FileIdentity` (`Identity`, `Strong`), `mkv.PinnedReader`,
  `mkv.ErrSourceChanged`, `HLSPlan.SourceID()`: what the plan's URLs serve,
  the source, the packaging (playlists and init segments, so the options) and
  the mkvgo version hashed, so two packagings of one file never share it.

### Fixed

- **A client that gives up on the window build it started no longer fails
  the clients waiting on that build.** The first request for a window ran the
  walk under its own context; when that client went away the walk was
  cancelled and every request waiting on it (a player fetching video and
  audio in parallel) got `context canceled` too. The build now runs under a
  context kept alive while anyone waits for it and cancelled only once the
  last of them has gone, for `Resource` windows and `Open` tables alike.
- **A plan refuses its media and subtitle segments once the source has
  changed.** Every read of the source for `Open`, `Resource`, `Segment` and
  the `.vtt` resources is bound to the file the plan was built on: a local
  file is verified on the open file itself at every read (`fstat`: size,
  mtime and the OS file identity, so a file renamed over the source with the
  same size and mtime counts) and its path stat'ed at most once a second per
  plan, a round trip on a network mount (open + `fstat` 1.8 ms, plus the path
  stat 2.6 ms per segment on an SMB share); a remote object (`httpfs`,
  `s3fs`) is read with `If-Match` on the ETag the plan saw, so a replaced
  object answers `412` and nothing of it is returned; any other FS is
  stat'ed before each read. A mismatch is `mp4.ErrSourceChanged` (the same
  value as the new `mkv.ErrSourceChanged`) instead of another file's bytes at
  the old offsets under the old ETag. `plan.SourceID()` names the file the
  plan was built on, for a URL prefix or cache key, and the streamed
  segments' weak ETag carries it. A plan without a stamp (`PlanGrowingHLS`,
  a source the plan could not stat) is not checked. Once seen, the change is
  final for the plan. The contract for a plan cache is in `docs/library.md`.
- **`httpfs` stats with one `HEAD`, never a window download.** `Stat` fetched
  the first 512 KiB window through a ranged `GET` to learn the size; it now
  sends one `HEAD` (one single-byte ranged `GET` where `HEAD` is not served)
  and reports `Last-Modified` as the mtime and the object's version
  (`mkv.FileIdentity`: the strong ETag, else `Last-Modified`). A plan over
  `httpfs` served through `Open` paid that window on every segment request.
- **An `httpfs` reader is bound to one version of an object.** Every window
  after the first is asked for the version the first one declared
  (`If-Match` on a strong ETag, `If-Unmodified-Since` on `Last-Modified`), or
  the one `Pin` (`mkv.PinnedReader`) set, and must carry that validator: a
  different one or a `412` is `mkv.ErrSourceChanged`, a missing one an error
  (a response without it was taken as the right version). Only a strong ETag
  derived from the bytes rules out mixed versions: S3 and MinIO send one;
  nginx and Caddy derive theirs from size and mtime, and a same-size,
  same-mtime replacement behind them is read as the old version (measured,
  documented).
- **An `httpfs` `206` is taken only when it is coherent.** Its
  `Content-Range` must start at the offset asked, end within the request and
  before its total, keep the total of the reader's first window (a moved
  total is `mkv.ErrSourceChanged`), and come with exactly that many bytes,
  read through a cap. A short body, an over-long body, an end past the
  request or the total, and a misplaced start were accepted; an empty `206`
  made `Read` return no bytes and no error forever, so `io.ReadFull` spun.
- **`PlanHLS` refuses a source replaced while it builds the plan.** The
  plan was stamped with the source's size, mtime and identity after it had
  read the file: a replacement between the two left a plan cut from one file
  and stamped with the other, whose later reads passed the check and applied
  the old offsets to the new bytes (reproduced by renaming another file over
  the source at each of the build's opens). The source is now stat'ed before
  the first read too, and a difference is `ErrSourceChanged`, also when the
  build failed on the new file's bytes. One more stat per plan: a `HEAD` over
  `httpfs`/`s3fs`, nothing per segment.
- **An `httpfs` reader no longer panics on an object that shrank.** A `416`
  for a range inside the size the reader knew left it without a window and
  `Read` sliced past it (`slice bounds out of range`); it is now
  `mkv.ErrSourceChanged`, and so is a `404` or `410` once the reader has seen
  a version or been pinned. A fresh reader's `404` stays a plain not-found.
- **`mkvhttp` conditional requests follow RFC 9110**: `If-None-Match` uses
  the weak comparison (a `W/` prefix on either side does not count), a `304`
  carries the `Cache-Control` of the `200` on every handler, and a streamed
  segment's `Range` is ignored under an `If-Range`, which its weak ETag can
  never satisfy, so the client gets the whole resource rather than a range of
  bytes it cannot validate.
- **The streaming copier's stage no longer grows past its pooled size.** A
  buffered span of a stage or more (a keyframe found in the read-ahead buffer
  when `sendfile` is not available) was packed with the small pieces before
  it, growing the stage to the span's size; it is now written on its own.
- **`RemuxToHLS` treats a segment head the writer takes short without an
  error as `io.ErrShortWrite`**, as the segment media already was.
- **`WriteRange` no longer relies on an unspecified evaluation order** for the
  count it returns after the final flush.

## [0.43.1] - 2026-10-11

### Fixed

- **`RemuxToHLS` removes the temp files it had created when creating the next

- **`ResourceHandle.WriteRange` refuses a range whose end overflows `int64`**

## [0.43.0] - 2026-10-11

### Changed

- **A streamed segment reaches the socket by `sendfile` above 16 KiB and by
  packed writes below.** `HLSPlan.Open`'s copier hands any span of 16 KiB or
  more to a writer that can read the source file itself (`net/http` turns it
  into `sendfile` on a plain TCP connection) and packs the smaller spans, the
  segment head and the stripped headers into 64 KiB writes instead of one
  `Write` per sample. Server CPU per video segment served over loopback, the
  same segments compared byte for byte with the pre-written files: a 43
  Mbit/s 2160p remux (37.6 MiB per segment) went from 8.6 ms to 2.3 ms, under
  `http.FileServer`'s 2.4 to 2.7 ms on the pre-written files; a 4.3 Mbit/s
  1080p encode (4.5 MiB) from 1.9 ms to 1.5 ms against 0.8 to 0.9 ms. A
  vectored write through `net.Buffers` was tried for the small spans and
  changed nothing: `http.ResponseWriter` does not expose `writev`.

- **`RemuxToHLS` writes each track's temp file through a 1 MiB buffer.** The
  first pass issued one `write` call per sample; a 28-minute 1080p episode
  made 145 000 of them, now 974, and its first pass dropped from 0.72 s to
  0.26 s of system time with the output byte-identical (1 311 and 3 879
  files compared on two real sources). The segment copy itself was measured
  and left alone: one `copy_file_range` per segment at 2 to 4 GiB/s, and a
  user-space buffer costs the same; the idle time seen at the end of a run
  is the kernel's dirty-page writeback, not the copy.

## [0.42.0] - 2026-10-10

### Added

- **`HLSPlan.Open` serves a media segment without holding it.** `Open(ctx,
  name)` returns a `ResourceHandle` (`ContentType`, `Size`, `ETag`,
  `WriteTo`, `WriteRange`, `Bytes`, `Close`): the plan walks the window's
  structure once (no video payload read), keeps a small table per window
  (sample positions, segment heads, and the audio renditions when they weigh
  under 2 MiB), and writes the segment from the source through one 256 KiB
  buffer, merging reads across gaps under 8 KiB. A slow client holds a
  buffer, not a segment: sixteen clients at 2 MB/s on a 57 Mbit/s 2160p remux
  went from 940 MiB to 28 MiB of resident memory. Tables are budgeted per
  plan (16 MiB) and per process (`SetTableCacheBytes`, 128 MiB). `Open` falls
  back to the buffered build, counted in `Stats().StreamFallbacks`, for MP4
  sources, encrypted or CENC output, converted tracks, custom `Options.FS`
  without `Options.StreamFromFS`, and compressed video tracks.
- **`mkvhttp.Handler` streams the segments of a plan that implements
  `Opener`**: exact `Content-Length`, a weak ETag from the source's size and
  mtime, one `Range` at a time, `HEAD`; an error after the status line closes
  the connection rather than ending a short body cleanly. `Options.Buffered`
  (CLI `serve --buffered`) keeps the previous path with its strong ETag.
- **`mp4.SetMaxConcurrentWalks(n)`** caps the window walks in flight across
  every plan of the process; the rest queue or give up with their context.
  `WalksInFlight()` reports the count, `Stats().SlotWaits` the walks that
  queued. CLI `serve --max-walks N`. Zero lifts the cap (the default).
- **A subtitle index derived from the Cues, without a walk.** Muxers cue every
  block of a subtitle track with its position inside the cluster
  (`CueRelativePosition`, now read into `CuePoint.RelativePos` and written
  back by the writer). `matroska.SubtitleIndexFromCues` builds the index from
  the metadata alone and reports, per track, whether its cue count matches a
  trusted `NUMBER_OF_FRAMES` statistic; the caller decides what to do with an
  unverified track. `Resolve` reads one cluster header per cued cluster and
  the index then serves and marshals like a built one. On a 2160p remux with
  6,371 cued PGS blocks the derived index matched the walked one block for
  block, for 0.1 MiB read against 14.6 GiB. The on-demand plan derives it by
  itself when no `Options.SubtitleIndex` is given and serves the verified
  tracks from it (`Stats().SubtitleCueIndexed`, `SubtitleCueUnverified`); a
  cue that does not land on its block falls back to the walk. CLI
  `subtitle-index -from-cues`. `mkv.TrustedTrackStatistics` is the shared
  statistics-tag check.
- **`Track.DecodePayload`** returns a block's content: inflated for zlib and
  bzlib, the stripped header restored, bounded at 8 MiB. `Block.DataOffset`
  gives the payload's absolute offset, in header-only mode too;
  `BlockReader.SetHeaderOnlyTracks` limits header-only mode to some tracks;
  `reader.ResolveClusterBlock` seats a reader from a cluster position and a
  relative offset.
- **Stats**: `ArenaFallbacks`, `TableBuilds`, `TableEvictions`,
  `StreamedSegments`, `StreamFallbacks`, `UndeclaredZlibBlocks`.

### Changed

- **Compressed tracks are decoded wherever their content is consumed.** The
  MP4 remux, the full HLS pass, the on-demand plans, the growing plan,
  `Demux`, keyframe extraction and the WebVTT renditions all inflate zlib and
  bzlib payloads and restore stripped headers; before, zlib audio and video
  reached the MP4 samples still compressed, and a zlib SRT track rendered
  garbage cues. lzo, which mkvgo cannot decode, is refused with a message
  naming the remedy, or dropped under `SkipUnsupported`. MKV-to-MKV copies
  still carry the blocks as stored, with their declaration.
- **`Fingerprint` hashes decoded content**: a header-stripped or compressed
  track now fingerprints the same as its plain remux. `CompareBlocks`, the
  `CONTENT_SHA256` tags, `Verify`, Join and Split keep hashing the stored
  bytes, so every file already tagged still verifies.
- **The master playlist of an on-demand plan declares its I-frame stream** at
  build time, with the first keyframe's size as the BANDWIDTH estimate; the
  line used to appear only after the I-frame playlist had been built.
- **The window arena is sized on the video's share of the span**: the other
  renditions' lightest rate seen comes off the buffer, so the arena no longer
  carries the audio's bytes as slack. A window the estimate undershoots is
  assembled by copy and lowers the estimate (`Stats().ArenaFallbacks`).

### Fixed

- **On-demand fragments overlapped by one frame duration at open-GOP
  boundaries.** The window's end time was the first PTS stored after the
  boundary, a leading picture's; it is now the lowest PTS of the next window,
  found by a bounded peek (16 blocks) that stops at the first trailing picture
  or keyframe. The I-frame playlist derives the same value from its windows.
- **The full pass shortened the last segment** when the final sample in
  decode order was not the highest PTS: the end is now the highest PTS plus
  the last duration.
- **A track that ended before the presentation's tail was given an invented
  final pair**: the tail probe now walks back one segment at a time,
  header-only, until it finds the track's own last blocks.
- **Grid-timed audio jittered by one frame at some window starts**: the
  running frame index now carries across windows like the full pass's clock,
  learned from the window before or wound up over it when the timecodes leave
  the grid.
- **Laced audio without a DefaultDuration drifted a tick a frame.** The
  frame stride was measured between the first two block timecodes, which are
  rounded to the millisecond: eight AAC frames read as 171 ms, 1026 ticks
  instead of 1024, and the audio timeline ran 0.2 % slow - 11 s late at the
  end of a two-hour film, the plan's init declaring a different duration than
  the full pass's. The frame size now comes from the stream itself - the AAC
  configuration's frame length and SBR rate, the E-AC-3 syncframe's block
  count, the DTS core header, the MP3 version, a fixed FLAC block size,
  TrueHD by specification - and the measured stride yields to it; a codec the
  stream does not size snaps to a known frame size within a percent, and one
  no table knows is measured over the whole track from a trusted
  NUMBER_OF_FRAMES count instead of two neighbouring blocks. A laced track
  nothing sizes at all has its frames spread over each block's span, the same
  in both modes, bounded to a block (`Stats().SpreadLacedTracks`; `diagnose`
  reports it as `unsized-laced-audio`). A permanent drift control in the
  tests compares every output presentation time with the source timecodes
  and every fixed-frame audio duration with the frame, in both modes.
- **Undeclared zlib on subtitle tracks.** Some muxers compressed PGS and text
  subtitles and dropped the `ContentEncodings`; the blocks then read as
  invalid display sets. A subtitle block whose track declares no compression
  but inflates to its end with a valid checksum is now served inflated
  (`Stats().UndeclaredZlibBlocks`), and `diagnose` reports the track as
  `undeclared-compression`. Audio and video are never sniffed; raw text that
  happens to open on a zlib header pair stays raw.

## [0.40.0] - 2026-10-06

### Added

- **`Options.SubtitleIndex`: an on-demand plan serves WebVTT from a prebuilt
  subtitle index.** A Matroska file indexes its video, not its subtitles, so
  a plan reached a subtitle track by walking the clusters around a segment -
  and the video in them: the first subtitle segment after a start or a seek
  read two to four minutes of the file (92 MiB on a real 1080p film, 244 MiB
  on a 2160p one) and the whole-track `subN.vtt` read the film. Given the
  index `matroska.BuildSubtitleIndex` builds once per file, the plan seeks
  straight to the track's blocks: the same WebVTT for a few kilobytes read.
  An index that is not the file's - another size, Segment UID or timecode
  scale, a track it does not cover, a position that does not hold what it
  recorded - is set aside and the walk serves; it never yields a wrong cue.
  `SubtitleIndex.Matches` and `SubtitleIndex.TrackBlocks` (with
  `reader.IndexedBlock`) are what the plan reads, through the
  `mp4.SubtitleBlockIndex` interface.
- **`HLSPlanStats.SubtitleWalks` and `SubtitleIndexedBlocks`** say which of
  the two paths served a plan's subtitles.

### Fixed

- **Planning a Matroska source no longer walks toward an audio track's
  second block.** An audio track without a declared frame duration had the
  plan read on until that track's next block, to learn a stride from it -
  which is only ever learned when the first block is a lace of several
  frames. A real 4 GB file stores its second audio track's next block 480 MB
  in: planning it read 481 MB and took 3.3 s before the first segment could
  be served. It now stops once that first block is known to hold one frame
  (the full pass applies the same rule): 0.5 MB, 14 ms. Every output is
  unchanged.
- **Reading an EBML number no longer allocates.** Every element and block
  header of a walk passed a small buffer through an `io.Reader`, which put it
  on the heap: some 35,000 allocations for one 2160p segment. A source that
  hands out single bytes is read byte by byte: about 650.
