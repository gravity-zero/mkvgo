# Changelog 0.70 to 0.79

Archived entries of mkvgo 0.70.x to 0.79.x, as they were published; a version moves here once a newer one ships. The current versions are in [CHANGELOG.md](../CHANGELOG.md).

## [0.72.0] - 2026-11-21

### Added

- `Options.SignedCompositionOffsets` (`--signed-offsets` on `to-hls`,
  `hls-segment`, `serve` and `serve-growing`): a reordered video's composition
  offsets are written signed, with no composition shift and no video edit
  list. A player that ignores the edit list showed the picture late by the
  reordering depth (84 ms on a two-frame pyramid). Off by default.

### Breaking

- The HLS/DASH init segment no longer carries the cover art: a large cover
  made it megabytes a player fetches before its first frame. Title and tags
  stay; `RemuxToMP4` still carries the cover.
- HLS/DASH bytes change for a video the fixes below concern: its init's edit
  list and its segments' composition offsets move together. Drop the cached
  init and segments of one source at once.

### Fixed

- HLS/DASH lost frames of a video that reorders deeper than its opening
  frames show: frames shared a presentation time and players dropped them, a
  quarter to a half of a segment's. The composition shift now covers the
  depth the parameter sets declare, and is measured past a first GOP of a
  frame or two.
- A video that reorders deeper than its parameter sets announce keeps every
  presentation time through a negative composition offset (`trun` version
  1); a reader that pulls its decode clock back for one presents that video
  later by it.
- A frame with a stray timestamp (it presents before more than 16 frames
  decoded ahead of it) presents at its decode time and moves no other
  frame's; full pass and on demand agree on it.
- A segment opens on its keyframe when a frame shares the keyframe's
  timestamp, and served on demand it keeps the frames stored between the two.

## [0.71.2] - 2026-11-20

### Fixed

- Under `WithInBandColourFallback` (`-in-band`, `mp4.Options.InBandColour`):
  an HEVC track declared bt2020-10 is read as HLG (`arib-std-b67`) when an
  Alternative Transfer Characteristics SEI of its first sample says so - the
  header alone made an HLG video an SDR one; an H.264 record with no SPS
  (`avc3`) gets its profile, level, pixel format and colour from the SPS its
  samples carry; an MPEG-2 track with no CodecPrivate gets its profile, level
  and pixel format from its first sample. Each such track costs one more
  bounded read under the option.
- A fragmented MP4 read head-only gets the first-sample fallback too
  (`mp4.Options.InBandColour`): its sample tables are empty, so nothing was
  read and an `avc3` or `hev1` track kept no profile, level or colour. The
  first `moof` is read for where the first samples are.
- An MPEG-2 CodecPrivate gives the profile, level and pixel format head-only,
  and a VP8 track its pixel format: they were empty.
- Bitmap subtitles: a DVB block fills and draws a full-size region and one
  picture of it, not four planes (254 bytes of block allocated 208 MiB); a
  block asking for more is passed over as damaged.
- A keyframe walk (`WithKeyframeIndex`, `keyframes -walk`) cancelled on its
  way returns the cancellation: it returned the keyframes met so far with no
  error.
- `concat-hls`, `concat-segment` and `PlanConcat` apply `--sub-offset`
  (`Options.SubtitleOffsetMs`): the option was accepted and ignored.

## [0.71.1] - 2026-11-20

### Fixed

- Under `WithInBandColourFallback` (`-in-band`, `mp4.Options.InBandColour`),
  three video tracks whose header names no colour now get it from their first
  sample, where they kept none or the wrong "determined": a VP9 track whose
  CodecPrivate holds the Matroska feature records, or whose Colour element
  states the range alone (the keyframe header was read only when the profile
  was missing); an AV1 track whose `av1C` holds no sequence header (a PQ
  video read as having no colour); an HEVC track whose `hvcC` holds arrays
  but no SPS. A VP9 Matroska file with no colour anywhere costs one more
  bounded read under the option.
- A VP9 keyframe header that says its colour is unknown sets
  `ColourDetermined`, as an H.264, HEVC or AV1 stream stating "unspecified"
  does: the colour was read, there is none to find elsewhere.

## [0.71.0] - 2026-11-20

### Fixed

- Stray bytes ahead of the first Cluster that happen to decode as an element
  header (the tail of an old tag an in-place edit before 0.56.0 could leave)
  no longer make `analyze`, `ingest -analyze` and `validate` report a complete
  file as cut short, or lose its first Clusters without a word: the block walk
  resynchronizes past them as the head reads do.
- A Void or CRC-32 ahead of the first Cluster declaring a few bytes too many
  no longer swallows the head of the element behind it: the readers
  resynchronize on that element instead of losing it without a word.
- `reindex --resync` and `salvage` keep the Info and Tracks that sit behind
  such bytes (the output had no track, exit 0), and `keyframes -walk` no longer
  loses the keyframes of the Clusters a stray size led it past.
- A few stray bytes between the last Cluster and the Cues or Tags closing a
  finished file (up to 64) end the block walk as the end of the media: such a
  file is no longer reported as cut short by `analyze`, nor refused by
  `demux`, `split`, `remove-track` and `fingerprint`. A longer run is still
  refused: it may hide a Cluster.
- `diagnose` no longer answers healthy when stray bytes sit between the head
  elements it reads and the first Cluster: it walks the head to the first
  Cluster.
- The strict `reindex`, `reindex-inplace` and `retime` refuse bytes that read
  as an element running past the end with the offset and the command that
  works (`mkvgo reindex --resync`), not `copy unknown 0x8C body: EOF` nor a
  "truncated file" pointing back at the command that refused.
- Bytes that read as a Cluster header too small to hold a block (8 bytes at
  most, opening with no element of a Cluster) are passed over as the stray
  bytes they are instead of refused as a damaged region, and `diagnose` counts
  them.
- `analyze` warns when the file it measured was read past undecodable bytes.
- What a strict block walk now reads past without an error, where it failed
  or lost media before: bytes ahead of the first Cluster that decode as an
  element whose size leads nowhere or that declare no size, the excess of a
  Void or CRC-32 that declares too much, 8 bytes at most read as a Cluster,
  64 at most before the closing elements. `Container.ResyncedBytes`,
  `validate`, `diagnose` and `analyze` say so for the head; a tolerant walk
  counts them all (`SkippedBytes`). `ReadStream` cannot look past an element
  and keeps skipping a header that decodes by its size.
- Bitmap subtitles: a block whose display sets together composite more than
  two subtitle planes is passed over as damaged (each composition had its own
  picture, 64 MiB for 30 bytes of block); a PGS object's buffer grows with
  its data instead of taking the 4 MiB its first segment may declare; a nil
  `SubtitleIndex` refuses `MarshalBinary` instead of panicking.
- Bitmap subtitles, again: a PGS block hands back two planes of pictures at
  most, not four (256 MiB for 115 bytes of block); a VobSub control sequence
  with no end command stops where the next one starts instead of running its
  header as commands (a picture forced on, at the wrong time); `extract-subtitle
  -format png` encodes a picture shown again once, each cue keeping its file.
- `to-mp4`, `to-webm`, `to-hls`, `demux`, `split` and `remove-track` warn when
  the Matroska source was read past undecodable bytes between its elements,
  and exit 3 under `--exit-damaged`: they said nothing.

### Changed

- A VobSub header with no `palette:` line (an old `.idx`, whose palette is in
  the `.ifo` beside it, or a track muxed from one) is read instead of refused:
  each picture is drawn in greys from black to white in the order of the pixel
  values it shows. A header with no `size:` line is still refused, and the
  refusal no longer speaks of a CodecPrivate for a `.idx` file.

### Added

- `Diagnosis.ResyncedBytes` (`resynced_bytes` in JSON): the bytes the head
  read passed over ahead of the first Cluster, so a caller needs no second
  read to count them. `WithWholeHead` (`reader` and `matroska`) gives the
  same count to a head read of its own. A Void declaring too much counts for
  its excess.

## [0.70.0] - 2026-11-19

### Changed

- Grid-timed audio whose timecodes run a frame ahead of the grid for a while
  is no longer described as experimental: measured in hls.js, Shaka and
  ExoPlayer, no player stalls on the window that absorbs the frame; Firefox
  keeps the audio up to about a frame late past it, as before 0.62.0
  (`docs/library.md`, HLS plan).

### Added

- `HLSPlanStats.SubtitleHarvestedClusters`: the clusters a subtitle rendition
  took its cues from as a window walk read them.

### Breaking

- Verdicts: `Playability` and `Ingest` send a PQ or HLG video with no
  mastering metadata or MaxCLL to transcode on a target without HDR (reason
  `HDR (PQ transfer) is unsupported on target`); it was direct-play before.
  They also read the first sample of a video track whose header states no
  colour, so a PQ stated only in the SPS counts.
- Bytes written: `PlanHLS` with `SynthesizeIndex` passes over a damaged region
  as the window walks do (`DamageBytes`) instead of ending the index there, so
  such a file's playlists change: the last window ran over the rest of the
  file (a 43 min episode with damaged regions planned 35 windows, the last
  served as one 2.2 GB segment; 309 now).

### Fixed

- `PlanHLS` without a subtitle index no longer walks the file again for each
  subtitle rendition: the cues come from the window walks, and a subtitle
  request builds the windows the video then serves from (over a network
  mount, half of what was asked of the source before). A 1080p episode
  played with one subtitle read 213 % of what was served, 113 % now (102 %
  without the subtitle); three subtitles cost what one does
  (`docs/library.md`, HLS plan).
- A window walk and a streamed segment no longer ask the disk to read ahead
  past the end of the file, and a remote source (`mkv.RangeHinter`) is no
  longer asked for an open-ended range: the plan's head peek and its last
  window hinted to `MaxInt64`.
- `AudioStartDelays` (and `Diagnose`) seek over what precedes the first
  cluster instead of reading it: the attachments, a subtitle's fonts often
  tens of MB, were read on every call. A cluster's declared size is no longer
  allocated before its bytes arrive (a 32-byte file declaring 200 MiB
  allocated 200 MiB).
- A block's declared size no longer allocates more than the bytes that arrive
  past 8 MiB (a 51-byte file declaring a 60 MiB block allocated 60 MiB on
  every walk that met it; 1 MiB now).
- `retime` and `reindex` no longer allocate a cluster's declared size before
  its bytes arrive (a 32-byte file declaring a 200 MiB cluster allocated it).
